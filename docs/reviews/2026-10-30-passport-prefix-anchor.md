# 여권 예외의 앵커 방향 제한

## 문제와 수정

`여권번호 M12345678 고객번호 M12345678`에서 뒤의 고객번호 라벨이
첫 번째 값에도 직접 연결된 것으로 인정되어 여권 후보가 제외될 수 있었다.
두 값의 문자열이 같아도 원문 위치는 다르므로 별개 탐지다.

L5 `passport_override_number()`에 `anchor_end <= start_idx` 조건을 추가했다.
이제 여권 예외에는 값 앞에서 직접 연결된 명확한 번호 라벨만 사용할 수 있다.
기존 원문/좌표 검증, 허용 라벨, tier, 동일 segment/span 조건은 유지한다.
공통 `has_direct_anchor()`, 면허 예외, 전체 priority 순서는 변경하지 않는다.

## 한계

- `M12345678은 고객번호` 같은 뒤쪽 라벨만으로는 여권 예외를 적용하지 않는다.
- 예외가 적용되지 않으면 기존 priority를 사용한다. 모든 번호 타입에서
  여권이 반드시 이기는 정책을 추가한 것은 아니다.
- 라벨의 의미나 번호의 실제 소유자를 일반적으로 판별하는 변경이 아니다.
- 영문자로 시작하는 주문/구매번호의 L4 미탐지는 변경하지 않는다.
- L7, 외부 API 호출, NER 모델의 동작은 이번 검증 범위 밖이다.

## 회귀 검증 범위

- 값 뒤 고객번호 라벨은 여권 예외를 만들지 않으며 공통 앵커 판정은 유지한다.
- 실제 L3 여권 정규식 인식기와 tier 매핑, L4 고객번호 인식기와 전역 좌표 변환,
  L5 stage를 연결해 위치별 분류와 TOKENIZE 정책을 검사한다.
- 번호 문자열의 반복/상이, 라벨 순서, 콜론/조사/줄바꿈, 후보 순서 변경을 검사한다.
- 전체 L3 서비스나 L7을 실행한 테스트는 아니다.

- 수정 후 resolver/앵커/위험 점수/L5 stage 및 신규 L3 정규식+L4+L5
