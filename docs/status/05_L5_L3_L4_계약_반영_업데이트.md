# L5 엔터티 계약 반영 업데이트

> 기준일: 2026-09-14 (KST)
> 대상 브랜치: `feature/risk-scoring`
> 범위: L5 위험 분류·점수·정책 코드와 L5 단위 테스트만 포함

## 1. 이번 업데이트 범위

최신 L3 엔터티 목록과 공유된 L4 엔터티 명칭을 L5 분류표에 반영했다. 이번 커밋에는
L4 NER 구현, L4 학습 결과, 공통 스키마 변경, CI 변경을 포함하지 않는다.

변경 대상은 다음 세 부분이다.

1. L5 엔터티 보호 분류 추가
2. 미등록 탐지 타입 fail-closed 처리
3. L5 단위 테스트 추가

## 2. L5 엔터티 보호 분류

### 2.1 직접 보호 대상

다음 타입은 단독 탐지 시 최소 80점, `HIGH`, `TOKENIZE`로 처리한다.

```text
PERSON_EN
PERSON_KO
DATE_OF_BIRTH
KR_PASSPORT
KR_FRN
KR_DRIVER_LICENSE
ACCOUNT_NUMBER
ADDRESS_ROAD
ADDRESS_LOT
ADDRESS_DETAIL
```

`DATE_OF_BIRTH`와 `ACCOUNT_NUMBER`의 현재 분류는 법률적 분류 선언이 아니라 보호 누락을 막기
위한 보수적 운영 분류다. 추후 팀 합의로 내부 분류명이 바뀌더라도 단독 탐지 시 토큰화되는
보안 속성은 유지해야 한다.

### 2.2 서비스 식별자

`KR_BRN`은 현재 운영상 서비스 식별자로 처리한다.

```text
최소 점수: 85
등급: HIGH
정책: TOKENIZE
```

사업자등록번호의 최종 운영 분류는 별도 합의가 필요하지만, 현재는 미등록 타입으로 빠지거나
원문이 그대로 통과하지 않도록 보수적으로 보호한다.

### 2.3 기존 지원을 유지한 L3 타입

| entity_type | L5 처리 |
|---|---|
| `LOCATION` | 지역 상세도와 QI 결합 평가 |
| `ADDRESS` | 직접식별자, TOKENIZE |
| `AGE` | 정확 연령 QI |
| `AGE_GROUP` | 연령대 QI |
| `KR_RRN` | 직접식별자, TOKENIZE |
| `PHONE_NUMBER` | 직접식별자, TOKENIZE |
| `EMAIL_ADDRESS` | 직접식별자, TOKENIZE |

## 3. 미등록 엔터티 fail-closed

기존 L5는 분류표에 없는 `entity_type`을 `GENERAL_INFORMATION`으로 판단했다. 이 경우 L3/L4가
새 타입을 추가했지만 L5가 갱신되지 않으면 보호 점수와 정책에서 누락될 수 있었다.

이제 `assess_risk()`는 탐지 결과에 미등록 타입이 있으면 다음 예외를 발생시킨다.

```text
ValueError: unsupported detected entity_type(s): <TYPE>
```

실제 파이프라인에서는 이 예외를 받아 L6/L7 진행을 중단해야 한다. 이번 커밋은 L5 평가
함수까지만 변경하며 파이프라인 예외 연결은 포함하지 않는다.

## 5. 추가한 테스트

- 신규 직접 보호 타입 10종이 80점·HIGH·TOKENIZE인지 검증
- `KR_BRN`이 85점·HIGH·TOKENIZE인지 검증
- 미등록 타입이 `ValueError`로 실패하는지 검증
- 기존 QI 점수, 결합 점수, 경계값, 민감정보 confidence 테스트 유지

## 6. 이번 커밋에 포함하지 않은 변경

다음 항목은 L3·L4 또는 공통 계약 소유 범위이므로 L5 전용 커밋에서 제외했다.

- L4 `PS → PERSON_KO` 어댑터 코드
- L4 segment-local offset 변환 코드
- L4 NER 학습·실험 파일
- 공통 `DetectionTier` enum 변경
- 공통 `DetectedPII` 스키마 변경
- CI 및 training dependency 변경
- 프로젝트 전체 및 다른 팀원의 진행상황 문서

L5는 해당 팀이 최종 출력을 제공하면 표준 `entity_type`을 받아 처리한다.

## 7. 아직 미흡한 부분

### 7.1 PD-005 Final Detection Schema

다음 공통 필드는 아직 확정이 필요하다.

- `segment_id` 필수 여부와 좌표 기준
- `original_value` 필수 여부
- `confidence`와 `score` 중 표준 필드
- `source`·`detector`·`recognizer_name` 표준화
- tier 필수 여부와 직렬화
- `normalized`·`normalized_value` 필드명

### 7.2 L3/L4 overlap·merge

PD-006이 미확정이므로 L5는 아직 중복·부분 중첩 detection을 정리하지 않는다. 특히 L3
`ADDRESS`와 L4 주소 구성요소, 주소 내부 `LOCATION`, 같은 span의 다른 타입에 대한 공식 winner
규칙과 fixture가 필요하다.

### 7.3 실제 runtime fixture

현재 테스트는 합성 `DetectedPII`를 L5에 직접 넣는다. 다음 실제 출력 자료가 필요하다.

- L3 13종 정상·음성·변형·중첩 fixture
- L4 확정 recognizer 출력 fixture
- 멀티 segment 전역 offset fixture
- L4 span별 confidence 포함 fixture

### 7.4 파이프라인 연결

현재 L5 함수의 fail-closed 검증은 구현됐지만 실제 L1~L9 파이프라인 연결은 남아 있다.

```text
L3/L4 탐지 결과 수집
→ span 검증
→ overlap resolver
→ assess_risk()
→ 실패 시 L6/L7 중단
→ 성공 시 L6 정책 실행
```

### 7.5 L5→L6 혼합 처리

현재 `policy_action`은 요청 전체에 하나만 존재한다. 직접식별자와 QI가 함께 있을 때 각 span에
`TOKENIZE`와 `GENERALIZE`를 어떻게 나눠 적용할지 L6와 계약을 확정해야 한다.

### 7.6 점수 캘리브레이션

현재 80/85점 보호 하한과 30/60 등급 경계는 초기 운영값이다. 대표 또는 합성 데이터셋으로
오탐·미탐과 정책 결과를 측정해 보정해야 한다.
